# 任务管理

任务是异步的：建成功 ≠ 下成功。这一层的工作是**看状态、按前置条件动作、把失败翻译成人话**。

## 七种状态

| 状态 | 含义 | 可做的动作 |
| --- | --- | --- |
| `waiting` | 排队中（并发位不足或被队列暂停） | `pause` `remove` |
| `downloading` | 传输中 | `pause` `remove` |
| `processing` | **收尾**：解密、写标签、下歌词/封面、生成封面 | 只能 `remove`，别当卡死 |
| `paused` | 用户暂停，断点已保留 | `resume` `remove` |
| `completed` | 完成，`filePath` 有值 | `remove`（可带 `deleteFile`） |
| `error` | 失败，`errorMsg` 有原因 | `retry` `remove` |
| `interrupted` | 进程重启前未完成任务 | `resume`（不消耗重试次数） |

`processing` 与 `interrupted` 最容易被误判：前者是正常的最后一步，后者等主人点恢复。

## 动作前置条件（不满足会报错，别硬试）

| 动作 | 允许的状态 | 失败文案 |
| --- | --- | --- |
| `pause_task` | `waiting` `downloading` | 「只有等待或下载中的任务可以暂停」 |
| `resume_task` | `paused` `interrupted` | 「只有暂停或中断的任务可以恢复」；队列整体暂停时另一条：「下载队列已暂停，请先恢复队列」 |
| `retry_task` | `error` | 其它状态不报错，返回 `{retried: false}` |
| `remove_task` / `remove_tasks` | 任意 | 任务不存在 |

`retry_task` 还有一条隐藏前置：同曲已有未结束任务时报「此歌曲已有未结束的下载任务」。遇到就先去处理那条，而不是反复重试。

## 重试的实际行为

```
retry_task(id)
├─ 同品质重试，retryCount += 1，从磁盘实测已下载字节续传
├─ retryCount 到 4 且不是收尾失败
│   ├─ autoDowngrade 开 → 降到下一档，downloaded 归零，retryCount 归零
│   └─ autoDowngrade 关 → 标记「重试次数已用尽」，返回 retried:false
└─ 无后续档位 → 「已无后续可用品质」
```

- 「收尾失败」（`下载收尾失败…`）不参与降级，会一直同品质重试——因为问题在文件写入/打标签，不在音源。
- 旧任务没有 `availableQualities` 时无法降级，提示「旧任务缺少可用品质信息，请重新添加下载」，此时正确做法是重新建任务。

## 异常处理树

按 `errorMsg` 的**实际前缀**分流，不要凭感觉猜。下面每条前缀都是在服务或历史任务里实测到的。

```
任务 error
├─「音质候选已耗尽，最后音质 X 获取链接失败: <原因>」
│   └─ 最常出现。所有可用档位都取流失败（不等于"没有这档"）。
│       <原因> 决定怎么办：
│       ├─「…账号无权限 / 不可用」→ 未登录或版权受限 → 登录 / 换平台
│       ├─「QQ 音乐拒绝提供下载链接（result=104003）…」→ 会员曲/已下架/登录过期 → 重新登录或换平台
│       └─「无法获取下载链接」→ 平台侧取流接口失败 → 换平台
├─「获取下载链接失败: <原因>」
│   └─ 还没走到降级就失败了。看冒号后的原因，处理同上。
├─「所选音质不可用」
│   └─ 建档时就失败：qualities 里根本没有该档（或传了文件名）→ parse_link 看档位 → 换档重建
├─「直链已过期…」
│   └─ 汽水/直链任务 → 回本机重新解析投递（见 qishui.md），无法就地修复
├─「重试次数已用尽」/「已无后续可用品质」
│   └─ 重试/降级路径已经走完 → 换平台或接受当前档
├─「旧任务缺少可用品质信息，请重新添加下载」
│   └─ 删任务重建
├─「下载队列已暂停…」
│   └─ 队列被整体暂停 → 让用户在界面恢复队列，单任务 resume 无效
├─「此歌曲已有未结束的下载任务」
│   └─ 处理那条任务，不要重试本条
├─「下载收尾失败…」
│   └─ 文件被占用/磁盘满/标签写入失败 → 检查磁盘空间、是否被播放器占用
├─ 网络类（超时、连接重置、5xx）
│   └─ 有限重试（1–2 次）→ 仍失败则告知，换平台或稍后再试
└─ 其它
    └─ 原样保留 errorMsg 反馈，不猜原因
```

**「音质候选已耗尽」是最容易被误读的一条**：任务记录里的 `quality` 会变成"最后尝试的那一档"（比如目标 `flac`、最后显示 `128kmp3`），这不是用户选了 128k，而是降级链走到了底。汇报时要说清"从 flac 一路降到 128kmp3 都取不到流，原因是账号无权限"。

重试上限：同一任务**不要连续重试超过 3 次**。降级已经发生两次还失败，通常是资源本身不可用。

## 查进度

```jsonc
list_tasks  →  TaskRecord[]
```

汇报时按状态聚合并给关键数字：

```
完成 12 · 下载中 2 · 排队 3 · 暂停 1 · 错误 2（共 20）
下载中：晴天 68% 1.2MB/s · 七里香 12%
错误：稻香（直链过期）、夜的第七章（音质不可用）
```

- 进度用 `downloaded / fileSize`；`fileSize` 为 0 时只报"进行中"。
- `speed` 单位是字节/秒，换算成 MB/s 再展示。
- 长任务别空转轮询：用户问的时候查一次；要看实时变化用 `GET /api/events`（`http-api.md`）。
- 已完成任务用 `filePath` 回答"存哪了"，不要自己拼路径。

## 控制动作的正确顺序

```
用户说"暂停那个" → 先 list_tasks 定位 taskId（按标题/歌手模糊匹配，多条要问）
                 → 校验状态是否允许
                 → pause_task
                 → list_tasks 复核（服务端可能因队列原因改写状态）
```

所有写动作都遵循 **定位 → 校验 → 执行 → 复核**。跳过"校验"会得到一堆无意义报错；跳过"复核"会在失败时误报成功。

## 批量控制

| 需求 | 做法 |
| --- | --- |
| 删掉所有失败任务 | `list_tasks` 过滤 `error` → `remove_tasks`（一次调用，不要循环单删） |
| 重试所有失败 | 过滤 `error` → 逐个 `retry_task`（有降级副作用，先告知） |
| 删除已完成并删文件 | `remove_tasks` + `deleteFile: true`，**执行前必须列清单让用户确认** |
| 暂停全部 | 只能逐条 `pause_task`，或让用户在界面暂停队列（HTTP/MCP 没有队列级开关） |

删文件是不可逆操作：列出 `filePath`、说明数量，等用户明确确认再执行。

## 队列与并发

- 同时下载数由设置 `maxConcurrent`（1–32）决定；超过的任务停在 `waiting`，这是正常的。
- 一直 `waiting` 且队列没暂停 → 并发位被占满，等或调大 `maxConcurrent`（`patch_settings`）。
- 队列级暂停只在界面/Tauri 侧有，MCP/HTTP 无法解除；遇到「下载队列已暂停」只能请用户操作。
